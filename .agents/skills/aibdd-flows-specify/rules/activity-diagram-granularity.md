# Activity 圖（流程）顆粒度

- 計數單位：對外產出之活動圖數量，以「一條可獨立驗收之業務流程」（一條 independent flow）為準，至多一張活動圖對應一條 flow。不得以 feature 檔案數、API 數、技術分層或模組邊界為由預設「一檔一圖」。
- 獨立流程：須具備可對使用者或驗收方陳述之進場條件／觸發與可驗收之終局（成功、失敗、或契約可述之中止）。僅列舉能力、規格項目或 feature 名稱而無明顯控制流主軸與狀態演進者，不另計為需獨立活動圖之流程。
- Rework 迴圈：退回→補件→再送→再審／再評估 等同一段業務旅程上之迭代，不得拆成多張活動圖。
- 同一 function package：多個 Actor 若處於同一條連續因果鏈、後段狀態依賴前段，通常收斂為單張活動圖；不得僅因角色標籤不同而增加張數。
- 純查詢／唯讀瀏覽：無業務狀態遷移、無獨立驗收里程碑者，不外拉獨立活動圖；敘述收斂於 feature／rule 即可。
- 合併 vs 拆開：當敘述上存在兩條可各自講完、入口或主線驗收點明顯不同之對外業務主線，得對應兩條 flow、因而兩張活動圖；若僅為同一主線下之變體強度（happy／極小／極大）或情境覆寫，優先以同張圖內分支／註記表達，不先膨脹張數。
- 依實際情境展開，顆粒度錨定在需求描述的行為空間：一張 activity 是使用者為達成一個目的（例：送出案件後最終獲得核准或駁回）而進行的一系列實際操作旅程；圖的顆粒度必須落在「需求為該旅程描述的完整行為空間」這一層，向上向下偏離都不對。向上偏（過度抽象）：以「是否符合條件」「是否已達最後層級」等泛化守衛節點加回跳迴圈，把需求已具體描述的操作與條件壓成看不見實際角色與條件值的純流程邏輯。向下偏（過度實例化）：把需求中的「標準範例」等單一數值實例當成整條旅程，只畫該實例走的一條路，或把實例級數值細節（評分明細、期望欄位值）寫進步驟文字。正確作法：需求已枚舉的條件分支全數出現在圖上（例：各額度區間對應之審核層級各成分支），步驟指回實際執行的角色與動作，分支條件引用需求中的實際條件（門檻值、狀態、規則結論、選項）；實例數值細節留給 feature 規則層。退回→補件→再送等需求本身以迭代描述的旅程段，仍依上方 Rework 迴圈規則以迴圈表達，不受本條限制。

# 反例

- 同一案件送出→遭退件→補件→再送→結案拆成兩張活動圖，把 rework 誤當第二條獨立流程。
- 同包內審核員核准與主管覆核實為串接之同一條審批鏈，卻因身分標籤拆兩張圖。
- 僅因存在三份 `.feature` 檔就畫三張活動圖，實際上只有一條使用者旅程與一組連續狀態。預期應一張圖涵蓋該 journey，多檔 feature 仍綁在同一 flow。
- 把儀表板列表／查詢獨立成張活動圖，而主敘事無狀態遷移之獨立驗收。預期應不另立圖，或併入具寫入／狀態改變之主流程之讀取段若必須出現在敘事中。
- 需求已具體描述一系列操作與其轉折條件（例：額度對照審核層級表——未滿 20 點至櫃檯主任、20 點以上加分館館長、50 點以上加區群總館長、100 點以上加副總館長、200 點以上加總館長），卻建模為「送出審核→是否最後一關→否則回跳」之泛化迴圈，實際條件值與各操作角色全數自圖上消失，圖只剩流程邏輯、無法當成情境對照需求驗收。預期應依需求的實際條件逐級展開分支（此例為 20／50／100／200 點），各 STEP 綁定實際操作角色。
- 把需求的「標準範例」單一數值實例當成整條旅程（例：spec 範例為資格積分 50 分換算 50 點，activity 就只畫 50 點走三關的一條路），需求已枚舉的其餘條件分支與對應角色全數消失，且步驟文字塞滿評分明細、期望欄位值等實例數值。預期應涵蓋需求枚舉之全部條件分支（此例為各額度區間之審核層級），實例數值細節留給 feature 規則層。
