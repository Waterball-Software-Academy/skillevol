# Actor 顆粒度

- Activity 圖以 UI-facing 人類或組織角色為主軸。
- 不得將產品內建系統、自有後端、排程、worker、資料庫列為獨立 Actor。
- 外部使用者（透過 UI／CLI 等由人主動操作觸發者）得是 Actor；同一 Activity 內 Actor 名稱唯一，domain 同一角色不得重複多列。
- 第三方系統僅當該段 flow 的入口為 Webhook、Callback、或邊界外服務主動打進來且為觸發端時，得為 Actor。
- Webhook／Callback 情境下，下游金流／寄信／一般外部 API 若發生在使用者已在 UI 觸發之後，不得升格為 Actor；其結果歸入觸發該流程之 Action 的 boundary／postcondition／對應 feature 之規則敘述。
- Actor 依實際情境具名化：activity 呈現的是使用者為達成某個目的、在應用程式上進行一系列實際操作的旅程；圖上的 Actor 必須是需求實際情境中執行這些操作的具名角色，需求以職稱、身分或名稱區分的操作者逐一列出。不得把需求已區分的多個操作角色收斂成「審核人」「處理人」「主管」等泛用身分——收斂後，旅程中每一步由誰操作、由誰驗收就無法對照需求指認。名稱唯一規則管的是同一 domain 同一操作者不重複多列；需求中不同身分屬不同 Actor，逐一列出不違反該規則。例：需求載明案件依序由櫃檯主任、分館館長、區群總館長、副總館長、總館長決策，此五者即各自成 Actor，而非合併為「審核人」。

# 反例

- 將排程器、訊息佇列 consumer、資料庫、自有後端服務 畫成與人類並列的 Actor，彷彿它們「主動開局」一條業務流程。
- 使用者在 UI 按下付款後，另立金流閘道、寄信服務為 Actor，與「已按付款的人」並列，把非入口的下游互動當成圖上獨立身分。
- 入口其實是使用者填表送出，卻額外畫 Webhook 接收端當主 Actor（若該段並非由邊界外主動觸發開局）。
- 同一 Activity 內同時出現「玩家」與「使用者帳號（或兩個稱呼不同、domain 上同一操作者），違反名稱唯一／不重複多列。
- 需求以不同職稱／身分區分一系列操作的執行者（例：案件依序由櫃檯主任、分館館長、區群總館長、副總館長、總館長決策），activity 卻以單一泛用身分（「審核人」）涵蓋全部操作，旅程看不出每一步由哪個角色操作與驗收。預期應把需求具名的角色逐一列為 Actor，各 STEP 綁定其實際操作角色。
