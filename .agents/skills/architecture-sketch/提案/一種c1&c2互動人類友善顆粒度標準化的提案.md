# Raw Idea

> 以下為提案人原始想法，逐字保留，不做改寫。

我有沒有機會寫一個互動式的網頁
他可以先餵入某種結構化資料
此結構化資料中呈現了此 architecture-sketch 架構全景.svg顆粒度的結構yml
然後網頁上可互動
主要是展開/關閉互動 over c2 & c1 level diagram

我想藉這機會 tune 一個我最喜歡的 c2 & c1 level class diagram顆粒度
把它變成生成網頁的標準，比起只生成 svg

這樣就更好讀，比較不會說有太跨越模組的 flow，使得凌亂
關閉模組時就顯示 cross-module critical dependencies
展開某模組時 cross-module critical  dependencies 變成 cross-module critical class 與 critical class 的依賴，然後模組內也會有模組內類別依賴

只要依賴對象的模組是開的，就是 class to class
否則就是 critical class to module or module to criticalclass


# Complete Proposal

> 狀態：草案（proposal）。本檔是 tracking artifact，不受「原始碼註解 as-is」規則約束。
> 上游關聯：`.claude/skills/architecture-sketch/`（DEFINE → VALIDATE → RENDER 流程）、
> `specs/truth/architecture/架構.yaml`（SSOT）、`specs/truth/architecture/架構全景.svg`（目前的靜態全景投影）。

## 0. 一句話

把 architecture-sketch 的輸出從「YAML（SSOT）+ 靜態 SVG」演進為「YAML（SSOT）+ **互動 HTML**」，
其中每個模組可展開／收合，而**依賴連線的顆粒度會跟著兩端模組的展開狀態自動升解／降解**——
讓讀者用「展開我關心的、收合其餘」的操作，得到剛好的細節、最少的跨模組視覺雜訊。

## 1. 動機（為什麼靜態 SVG 不夠）

目前 `架構全景.svg` 把 C2 模組總覽與 7 張 C1 類別圖拼在一張畫布，並用長箭頭把跨子圖的類別連起來。
它能一眼看到全部，但有兩個結構性限制：

1. **顆粒度被固定死。** 一張圖只能選一個細節層級。要嘛全是模組（看不到類別），要嘛全是類別（線太多）。
   讀者無法說「我現在只想看清楚『引擎』內部，其餘模組請縮成一個盒」。
2. **跨模組 flow 一多就凌亂。** 當所有類別同時攤開，class↔class 的長線會交錯成一團；
   但其中真正承載架構約束的只有少數幾條（critical）。靜態圖無法「平時只顯示關鍵、需要時才展開細節」。

互動網頁解掉這兩點：顆粒度變成**讀者可調的狀態**，而雜訊量隨之自動收斂。

## 2. 核心構想：依賴的 Level-of-Detail（LOD）投影

這是本提案的心臟。把「模組是否展開」當成狀態，讓**每一條依賴邊的兩個端點，各自跟著自己所屬模組的展開狀態，決定要呈現成 class 還是 module**。

### 2.1 名詞定義

- **Module（C2 節點）**：一個可展開／收合的容器，綁定一個實作單元（package/module）。對應現行 Sketch 的 C2 node。
- **Class（C1 節點）**：模組內部的類別／函式單元，綁定一個 file/class。對應現行 Sketch 的 C1 node。
- **Critical Class（關鍵類別）**：模組對外的「接點面」——被其他模組依賴、或承載跨模組契約的類別。
  當模組收合時，它就是代表整個模組對外講話的那張臉。例：`engine` 的 `applyMutation`、`genome` 的 `scope`/`refs`、`agent` 的 `runTurn`、`sdk` 的 `SdkPort`。
- **Critical Cross-Module Dependency（關鍵跨模組依賴）**：跨越模組邊界、且承載架構約束的依賴（呼叫／型別參照／資料流）。
  例：`runTurn → applyMutation`、`wf → scope`、`scope → refs`（反向耦合）、`applyMutation → «Mutator»`。
  非 critical 的跨模組依賴預設在收合視圖**隱藏**，以降噪。
- **Intra-Module Dependency（模組內依賴）**：模組內 class↔class 的依賴，只在該模組展開時才出現。

### 2.2 端點降解函數

對任一依賴端點 `e`（它指向某個 class `c`，`c` 屬於 module `m`）：

```
render(e) = c          若 m.expanded == true
          = m          若 m.expanded == false   // 降解為整個模組盒
```

### 2.3 一條邊的呈現規則

設依賴 `d` 從 `srcClass@srcMod` 指向 `dstClass@dstMod`，則畫出的邊為：

```
edge(d) = render(src) → render(dst)
```

由此自然衍生**四種邊態**（正是原文要的語意）：

| srcMod | dstMod | 呈現的邊 |
|---|---|---|
| 展開 | 展開 | **class → class**（最細）|
| 展開 | 收合 | **class → module**（critical class 指到對方模組盒）|
| 收合 | 展開 | **module → class** |
| 收合 | 收合 | **module → module**（最粗；多條 critical 依賴 roll-up 成一條）|

> 即原文：「只要依賴對象的模組是開的，就是 class to class；否則就是 critical class to module or module to critical class。」

### 2.4 可見性規則（哪些依賴該出現）

```
全部收合（C2 視圖）            → 只顯示 critical cross-module dependencies，且 roll-up 成 module↔module
展開某模組 M                   → M 的 critical 依賴細化成 class↔(class|module)；M 內部冒出 intra-module 依賴
non-critical cross-module dep  → 僅當「兩端模組皆展開」時才顯示（否則隱藏，避免細節噪音）
```

roll-up（合併）規則：當多條 critical class 依賴在收合後都變成同一對 `module→module`，合併為一條，
邊上標數量或代表性 verb（例：`engine → genome ×2（adhereOf / resolveRef）`）。

### 2.5 小範例（用 abathur.skills 自身）

- **全收合**：看到 `對話 → 編排`、`編排 → 引擎`、`引擎 → 變異子`、`引擎 → 基因組`（紅，roll-up 自 wf→scope/refs）、`基因組 → 版面`（紅）等少數 module↔module critical 線。乾淨。
- **只展開「引擎」**：`編排 → 引擎` 升解成 `runTurn（收合·編排盒）→ applyMutation`；
  引擎內部冒出 `applyMutation → wf`、`applyMutation → Mutator`、`EvolutionSession → canonical`；
  `wf → scope` 因「基因組」仍收合而呈現 `wf → 基因組盒`（class → module）。
- **再展開「基因組」**：上面那條變成 `wf → scope`（class → class），且 `scope → refs` 反向耦合的關鍵線現形。

## 3. 結構化輸入：擴充 Sketch Grammar

沿用 architecture-sketch 既有語彙（lanes / impl / notes / 五種 note type / granularity law），新增「模組內含 class」與「critical 標記」「class 級依賴」。建議形狀（strict YAML）：

```yaml
plan: "<title>"
levels: { module: C2, class: C1 }      # 宣告兩層對應

modules:                                # = 現行 C2 nodes
  - id: engine
    label: "引擎"
    lane: core
    impl: { unit: "src/engine", kind: module }
    notes: [ { type: behavioral-contract, text: "applyMutation 六關卡…" } ]
    classes:                            # = 現行 C1 nodes，下鑽即此清單
      - id: applyMutation
        label: "applyMutation"
        critical: true                  # ← 收合時代表此模組對外的接點
        impl: { unit: "engine/transaction.ts", kind: file }
        notes: [ { type: design-constraint, text: "純函數、全有或全無" } ]
      - id: wf
        critical: true
        label: "wf"
      - id: canonical
        critical: false                 # 非 critical：只在 engine 展開時才見

dependencies:                           # 一律以 class→class 宣告（最細真相）
  - { from: agent.runTurn,  to: engine.applyMutation, kind: call,  critical: true,  verb: "applyMutation(G,call)" }
  - { from: engine.wf,      to: genome.scope,         kind: call,  critical: true,  verb: "adhereOf/consumersMap" }
  - { from: genome.scope,   to: layout.refs,          kind: call,  critical: true,  verb: "resolveRef", note: "反向耦合" }
  - { from: engine.applyMutation, to: engine.canonical, kind: call, critical: false } # intra-module
```

要點：
- **依賴一律以 class→class 宣告**（資料保有最細真相）；module↔module 邊是執行期由 LOD 規則 **推導 / roll-up** 出來的，不另外手寫，避免兩份真相不一致。
- `critical: true` 同時供兩用：標記 critical class（收合時的代表臉）與 critical dependency（收合時唯一可見的跨模組線）。
- 其餘欄位（lane / impl / notes / note type / salience）直接沿用現行 grammar 與 skin；granularity law 不變（每盒 1–2 約束）。

## 4. 互動模型

- **展開／收合**：點模組標題列切換 `expanded`；提供「全展開 / 全收合 / 焦點模式（只展開選中，其餘收合）」。
- **依賴重算**：每次狀態變動，依 §2 規則重投影所有邊（class↔class / class↔module / module↔module）並 roll-up。
- **高亮**：hover 一條依賴或一個 class，沿依賴鏈高亮上下游（跨模組亦然）。
- **錨定的 note 與 impl chip**：沿用 skin；note 隨其錨定的 class/module 一起展開或收合。
- **可選匯出**：把當前 LOD 狀態「拍扁」成一張 SVG（即現行靜態輸出，變成此互動視圖的某個快照）。

## 5. 佈局與渲染

- 模組為容器盒（收合＝單一盒、展開＝長出 class 子盒並撐開容器）；自動重排其餘模組避免重疊。
- 邊路由：收合時連到模組盒邊緣；展開時連到 class 盒邊緣（端點裁切沿用 `架構全景.svg` 已驗證的「中心 ± 半寬/半高」算法）。
- 沿用既有 SKIN：暖紙底、UML marker（realize 三角／diamond）、note 五色、★ salience、紅＝反直覺耦合。
- 視覺降噪：non-critical 線預設隱藏；critical 線恆顯；roll-up 邊標數量。

## 6. 與現行 architecture-sketch 的關係

- **輸出契約演進**：原本「1 份 YAML + 1..* 靜態 SVG」→ 提議「1 份 YAML（SSOT）+ 1 份互動 HTML（投影）」；
  SVG 降為「某一 LOD 快照的匯出格式」，仍可保留。
- **DEFINE / VALIDATE 不變**：仍寫 strict YAML、仍跑 `validate_sketch.py`（需擴充：認得 `modules[].classes[]` 與 `dependencies[]`、檢查 class→class 端點存在、critical 標記合法、granularity law）。
- **RENDER 改為產 HTML**：新增一支 renderer（HTML+JS）吃同一份 YAML，內建 §2 的 LOD 投影引擎。

## 7. 標準化目標（這正是「tune 我最喜歡的顆粒度」的落點）

把以下三條凝固成「生成互動網頁的標準輸入顆粒度」：

1. **兩層固定**：module（C2）內含 class（C1），不再多層；每盒仍守 granularity law（1–2 約束 / impl）。
2. **critical 是一等公民**：每個模組標出它的 critical class（對外接點），每條跨模組依賴標出是否 critical。
   這組標記就是「收合時要顯示什麼」的唯一依據——也是降噪的開關。
3. **依賴只寫最細（class→class）**：粗顆粒度一律由 LOD 規則推導，杜絕 module 級與 class 級兩份真相打架。

達成後，「生成網頁」取代「只生成 SVG」成為預設輸出：更好讀、雜訊隨焦點自動收斂、且仍可一鍵拍扁成 SVG。

## 8. 開放問題（待定）

- critical 的客觀判準：是否可由「被跨模組依賴 ≥ 1 次」自動推導，而非全靠手標？
- roll-up 邊的標籤策略：顯示數量、代表 verb、或可展開的 tooltip？
- 焦點模式下的自動佈局穩定性（展開／收合時避免大幅跳版）。
- 是否支援第三層（C4 系統情境 / C3 容器）的同套 LOD，往上一層收合成系統盒。
- 驗證器要新增哪些不變式（端點解析、critical 一致性、孤兒 class、雙向真相衝突偵測）。
