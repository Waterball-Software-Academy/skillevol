# 逐點推進與修正規則

依使用者對某個驗證點的回應推進或修正時，依本檔。核心是不傾倒、把「不」當訊號、隨手歸檔。

## Rule 1 — 只在驗證點被確認後，才產出依賴它的 artifact

- 一個 artifact（unit 檔、shared、報告格式…）只在它所依賴的驗證點被使用者確認之後才產出，絕不預先把整批東西做好再一次交付。預先傾倒會逼使用者一次否決一大堆，痛苦之餘還會誘使雙方勉強接受校歪的尺。

### Good

情境: 形狀驗證點剛被確認，但第一個 happy unit 的設計還沒對齊。

只先產出與形狀相關的東西（例如工作區與點序），happy unit 的檔等它自己的驗證點確認後再寫。

結果: 每個產出都站在已確認的假設上，使用者不會被迫整批 reject。

### Bad

情境: 形狀剛確認。

趁勢一口氣把 happy、負向、holdout 三個 unit 的 before/expect/after 全寫好交付。

預期改法:

- 收手，只產出已確認驗證點所需的最小 artifact，其餘等各自的點確認後再寫。

## Rule 2 — 使用者說「不」要當成上游假設錯，定位、修正、記錄

- 使用者對一個驗證點說「不」不是挫敗，而是訊號：代表某個假設錯了。要回頭定位是哪個假設、據此修正後續的驗證點，並把這次修正記進 working-plan 的修正歷史（原本以為什麼、其實是什麼、改成什麼），不硬幹也不繞過。

### Good

情境: 使用者否決了「嵌套形狀」那個驗證點。

定位出是「before/ 該裝什麼」理解錯，重畫形狀、連帶調整後面依賴它的 unit 點，並在修正歷史記下這次更正，再重新呈現。

結果: 錯誤在最便宜的點被攔下，且留下可追溯的軌跡。

### Bad

情境: 同上。

把使用者的「不」當成小意見，微調一下用詞就繼續往下寫 unit，不回頭追是哪個假設錯、也不記錄。

預期改法:

- 把「不」當成上游假設錯的訊號，定位、修正後續點、寫進修正歷史後再續。

## Rule 3 — 每輪推進後，立即同步 working-plan 的進度

- 每次某個驗證點被確認、或計畫被修正，就立刻更新 working-plan 的「現階段／下一步」，讓檔案隨時反映實況。跨輪對話或 compact 後，要靠這份進度還原卡在哪、下一步是什麼。

### Good

情境: 剛確認完「可跑骨架」驗證點。

馬上把 working-plan 的現階段改成「驗證點 N（happy unit 設計）待確認」、下一步寫成對應動作，再進下一點。

結果: 任何時間點打開 working-plan，都能看出進度與下一步。

### Bad

情境: 連續確認了三個驗證點。

一路往下做，working-plan 的進度還停在第一個點，現階段與實況脫節。

預期改法:

- 每確認或修正一次就同步進度，不要累積到最後才補。
