# Rule 1 -- 使用 AskQuestion，一次一題、依序處理

## Good

情境: 呼叫方傳入三個待澄清項目。

執行方式: 每個待澄清項目各呼叫一次 AskQuestion；收到答案後再處理下一題，不批次合併。

## Bad

三個待澄清項目合併成一次 AskQuestion 送出，PM 難以對照上下文逐題決策。

一次提問後未等使用者回答就假設預設選項，直接寫入產出物。

# Rule 2 -- 用詞白話，對象是 PM

## Good

問題: 「學員剛加入 CRM 時，誰負責決定他走哪條培育流程？」

選項:
- 管理者手動分配（推薦：較符合目前「重新分配」由管理者操作的描述）
- 系統依學員來源自動分配
- 客服人員在首次聯繫時決定
- 其他（請自行說明）

## Bad

問題: 「學員 journey 的 initial assignment trigger 由哪個 actor 的 workflow 負責？」

選項含 CRUD、webhook、state machine 等 PM 難以判斷的技術詞彙。

# Rule 3 -- 選項 2 到 4 個，且須含「其他」

## Good

四個選項: 三個具體方案 + 「其他（請自行說明）」。

三個選項: 兩個具體方案 + 「其他（請自行說明）」。

## Bad

僅一個選項，或五個以上選項（不含「其他」）。

有 2–4 個具體選項但缺少「其他（請自行說明）」，使用者無法填寫規格未列出的答案。

# Rule 4 -- 問題須簡述上文脈絡

## Good

問題: 「在『安排買課預約』這段流程裡，客服幫學員排好試聽時間後，管理者要怎麼收到通知？」

## Bad

問題: 「通知方式？」（未說明是哪個流程、哪個角色，PM 無法對照上下文作答）

# Rule 5 -- 至少一個（推薦）選項並附簡短原因

## Good

- 系統內通知（推薦：管理者不需離開 CRM 即可處理排課）
- Email 通知
- 其他（請自行說明）

推薦理由寫在該選項括號內，一兩句白話，說明為何較符合已知需求或常見作業方式。

## Bad

四個選項皆無推薦標記。

推薦理由寫成獨立段落或技術長文，未放在選項括號內。

# Rule 6 -- 每題 Q&A 須完整留存

## Good

每完成一題 AskQuestion 後，留存一組紀錄:
- Question: 向 PM 提出的白話問題全文（含上文脈絡）
- Answer: 使用者選擇的選項文字；若選「其他（請自行說明）」則記錄其自行輸入的全文

澄清結束後將全部 Q&A 交回呼叫方 skill，由其寫入對應產出物。

## Bad

只更新呼叫方產出物中的待澄清標記，未留存 question / answer 紀錄。

Question 只寫待澄清原文而非實際向 PM 提問的白話句。

Answer 只寫選項 id（如 `option_b`）而非 PM 可讀的完整答案文字。
