# 提出指標 - 詞彙認知循序漸進

為了解決 skill 讀起來像內部 protocol、術語先於理解、上層 SOP 被不必要概念污染的問題，
提出 skill mutation 必須針對 `詞彙認知循序漸進` 指標去最佳化。

## 描述

詞彙認知循序漸進衡量一個 skill 是否先用一般使用者能理解的詞彙與句構建立操作直覺，再按需要載入 skill-specific 詞彙與定義。

此指標的核心判準：

一個詞第一次出現在讀者面前時，讀者是否已經能從一般語境理解它要做什麼？

若答案是「能」，該詞彙放置合理。若答案是「不能，但當下有快速解釋或當步規則引用」，可接受。若答案是「不能，而且只是內部術語裸露」，則違反本性質。

本性質不是禁止術語。它要求術語按 cognitive load 漸進揭露：先讓人知道要做什麼，再讓人知道這套系統把它稱作什麼。

## 基礎通用認知詞彙

基礎通用認知詞彙指一般使用者在沒有讀過本 skill 專有 glossary 前，也能理解的操作詞與物件詞。

### 操作詞

優先使用這類詞作為上層 SOP 與使用者訊息的主動詞：

- 讀取
- 建立
- 更新
- 寫入
- 檢查
- 判斷
- 選擇
- 比對
- 確認
- 等待
- 停止
- 回報
- 執行
- 修正
- 刪除

### 物件詞

優先使用這類詞描述上層產物：

- skill
- 檔案
- 資料夾
- 測試
- 測試結果
- 報告
- 規則
- 樣板
- 步驟
- 目標
- 問題
- 缺口
- 失敗
- 修改範圍
- 下一步

### 基礎句構

上層 SOP 與使用者訊息優先使用下列句構：

1. 先 X，再 Y。
2. 若 A，進入 B；否則進入 C。
3. 用 X 產出 Y。
4. 把 X 寫到 Y。
5. 檢查 X 是否符合 Y。
6. 等使用者確認 X 後，再做 Y。
7. 若缺少 X，停止並回報需要補 X。
8. 根據 X 選擇 Y。

這些句構的共同特徵是：讀者不用先知道內部名詞，就能看懂動作、條件、產物與下一步。

## skill-specific 詞彙

skill-specific 詞彙指離開本 skill 或本工作流後，一般使用者不一定知道的詞。

例子：

- eval
- oracle
- red gate
- provenance
- mutation
- mutator
- active gate
- state carrier
- holdout
- benchmark
- working-plan
- progressive disclosure

這些詞不是不能用，而是不能裸露在讀者尚未建立語境的位置。

## 三種處理方式

### 1. 首次提到時快速解釋

當術語會在後續重複使用，且用一兩句就能建立語境時，在第一次出現時用白話解釋。

格式：

```
<白話功能描述>，稱為 `<術語>`。
```

Good：

```
需要建立一組可反覆驗證此 skill 成效的測試，稱為 `eval`。
```

Bad：

```
建立 eval。
```

原因：Bad 在讀者還不知道 eval 是什麼時，直接要求建立 eval。

### 2. 在當步載入規則檔案

當術語背後不是一句定義，而是一整組判準、格式、例外與範例時，不要把定義塞進 SOP。
SOP 只寫當步要做的事，並引用該步真正需要的 RuleFile。

Good：

```
建立一組驗證此 skill 成效的測試。關於測試集合的結構與判準，請嚴格遵守 `rules/eval-rules.md`。
```

Bad：

```
建立 eval，eval 是 golden benchmark、fitness oracle、unit、scenario、variant、expect、after 等概念的集合。
```

原因：Bad 把一整套 glossary 塞進單一步驟，讀者還沒開始做事就被術語壓住。

### 3. 放棄此詞彙，改用流程表達

若術語只是內部分類名，沒有幫助讀者更準確執行，就放棄它，用流程句表示。

Good：

```
若測試報告沒有指出哪個檔案、步驟或規則出錯，停止並要求補強報告。
```

Bad：

```
若 provenance insufficient，停止。
```

原因：Bad 的術語沒有降低歧義，反而要求讀者先知道 provenance 是什麼。

## 指標

### 1. First-Mention Clarity

衡量 skill-specific 詞彙第一次出現時是否已被理解。

評分：

- 1.0：第一次出現前或同句內已有白話解釋。
- 0.7：第一次出現後的鄰近句有解釋，不影響執行。
- 0.3：文件稍後才解釋，但讀者在第一次遇到時需要猜。
- 0.0：全文未解釋，或只用另一個術語解釋。

### 2. Top-Level Plainness

衡量 frontmatter、Purpose、SOP phase 標題與頂層 step 是否優先使用基礎通用詞彙。

評分：

- 1.0：上層可直接用一般詞彙理解，不依賴 glossary。
- 0.7：有少量術語，但已快速解釋或被熟悉動作包住。
- 0.3：上層充滿術語，仍可靠上下文勉強猜。
- 0.0：不讀 glossary 就無法知道要做什麼。

### 3. Term Necessity

衡量每個 skill-specific 詞彙是否真的值得保留。

判斷問題：

1. 這個詞是否會重複出現？
2. 這個詞是否能縮短後續指令而不降低理解？
3. 這個詞是否對評分、產物格式或跨檔案引用有穩定身份？
4. 若改成白話流程句，是否更清楚？

評分：

- 1.0：術語必要，且能讓後續指令更短、更準確。
- 0.7：術語有幫助，但可以再補白話。
- 0.3：術語只是內部習慣，用流程句會更清楚。
- 0.0：術語沒有必要，且造成理解負擔。

### 4. Rule Loading Locality

衡量術語相關定義是否只在需要它的 step 被載入。

評分：

- 1.0：術語的細部規則只掛在會消費該概念的 step。
- 0.7：規則大致局部，但有少量上層提前暴露。
- 0.3：定義被放在共用區，所有讀者都被迫先看。
- 0.0：術語定義散落多處，且互相重複或矛盾。

### 5. Sentence Structure Plainness

衡量句子是否用基礎句構呈現動作、條件、產物與下一步。

評分：

- 1.0：每句都能看出誰做什麼、用什麼、產出什麼、接著去哪。
- 0.7：大致清楚，但有少量名詞化抽象。
- 0.3：多數句子是抽象名詞堆疊，需要讀者反推動作。
- 0.0：句子只像 protocol label，不像可執行指令。

## Gate / Reward 建議

### Veto 條件

1. frontmatter description 裸露未解釋的 skill-specific 詞彙，且不是廣泛通用技術詞。
2. Purpose 第一段依賴 glossary 才能理解 skill 的用途。
3. SOP phase title 或頂層 step 只有內部 gate id，沒有白話動作。
4. 使用者訊息直接要求確認 `confirm-xxx`，但沒有說明要確認什麼。
5. 同一術語在多處有不同定義。

### 建議門檻

1. First-Mention Clarity 平均分 >= 0.80。
2. Top-Level Plainness 平均分 >= 0.85。
3. Term Necessity 低於 0.50 的術語應刪除或改寫成流程句。
4. Rule Loading Locality 低於 0.70 時，應把共用定義移到當步 RuleFile。

## GOOD / BAD 校準

### GOOD

```
在新增或修改測試前，先用白話問使用者：我打算補的這條測試，是否真的在測你在意的問題。這個確認點記為 `confirm-failing-test-plan`。
```

原因：先講人要確認什麼，再給內部 gate id。讀者不需要先懂 gate id。

### BAD

```
補 failing test 前，必須先取得 `confirm-failing-test-plan`。
```

原因：`failing test` 與 `confirm-failing-test-plan` 都先於理解出現，讀者不知道要確認什麼。

### GOOD

```
若測試報告沒有指出哪個檔案、步驟或規則出錯，停止並要求補強報告。
```

原因：用一般詞彙描述 failure provenance 的效果，讀者能直接執行。

### BAD

```
若 provenance insufficient，停止並要求補強 eval。
```

原因：句子短，但理解成本高；需要先知道 provenance 與 eval 的定義。

## 與 mutator 的關係

優化此指標時，常見修法：

- `rename`：把裸露術語改成白話動作名。
- `inline-define`：首次提到術語時補一行短定義。
- `rewire-ref`：把術語細部定義移到當步 RuleFile。
- `delete-term`：刪掉沒有必要的術語，改成流程句。
- `split-glossary`：把過大的 glossary 拆成局部規則檔，避免所有 step 共同載入。
- `sop-rewrite`：把 phase title 或 step 從 protocol label 改成一般人能理解的動作句。
